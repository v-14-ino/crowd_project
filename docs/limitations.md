# Limitations and Future Improvements

This document outlines the current limitations of the Municipality Crowd Verification prototype, its evaluation constraints, and the necessary steps required before a production deployment.

## 1. Prototype and Implementation Limitations

- **Simulated Citizen Reports and Corroborating Sources:** The system currently operates on simulated data generated by scripts (e.g., `seed.py`). It does not yet ingest live API data from real-world citizen mobile apps or live IoT sensor networks.
- **Rule-Based VerificationEngine:** The `VerificationEngine` uses deterministic, hardcoded rules to calculate confidence and priority. While highly explainable and efficient, it lacks the nuance of a machine learning model that could adapt to historical patterns or complex multi-variable interactions (e.g., identifying organized malicious reporting campaigns).
- **Authentication/Security:** The current authentication implementation uses a simplified prototype JWT login. It lacks robust production security measures such as multi-factor authentication (MFA), role-based access control (RBAC) across different municipal departments, and rate-limiting to prevent API abuse.
- **Browser GPS/Location Limitations:** The frontend relies on the HTML5 Geolocation API, which can be inaccurate, spoofed, or denied by users. The system explicitly handles missing coordinates, but cannot currently detect or prevent sophisticated GPS spoofing.
- **Evidence Quality and Availability:** The system processes metadata about evidence (e.g., "Source Status") but lacks advanced image analysis (e.g., computer vision) to automatically verify if an uploaded image actually depicts the reported issue.
- **Freshness/Time Handling:** The current freshness logic (Fresh: ≤24h, Aging: 24h-72h, Stale: >72h) uses static global thresholds. These thresholds may be too long for critical issues (e.g., exposed live wires) or too short for long-term chronic problems (e.g., slow structural degradation of a bridge).

## 2. Evaluation and Operational Limitations

- **Limitations of the Validation Dataset:** The offline evaluation uses an artificially constructed dataset injected with synthetic noise and edge cases. It does not perfectly reflect the statistical distribution or chaotic nature of real-world municipal reporting.
- **False Positives and False Negatives:** 
  - *False Positives:* Coordinated malicious reporting by users could artificially inflate the confidence score of a non-existent incident, as the rule-based engine trusts volume and clustering.
  - *False Negatives:* A highly critical but isolated incident reported by a single user in a rural area with no sensors may receive a low confidence score, potentially delaying response.
- **Responder Verification Dependency:** The system relies heavily on a "human-in-the-loop" Phase 2 verification. If the municipal officer queue is backlogged, incidents will remain stuck in a "Corroborated" or "Pending" state, bottlenecking the resolution process.
- **Simulated Experiment vs. Real Deployment:** The prototype evaluation proves the core logic in a vacuum. Real-world deployment will face unpredictable user behavior, fluctuating reporting volumes during crises (e.g., storms), and complex municipal jurisdictions that the current prototype does not model.
- **Pending Stakeholder Validation:** The usability of the system has not yet been validated by actual municipal officers or citizens. The current UI workflows are based on assumptions of stakeholder needs and must undergo formal user testing before finalizing the design.

## 3. Infrastructure and Scalability Limitations

- **Local/Low-Cost Infrastructure:** The system is currently designed to run on local environments or low-cost singular instances using SQLite.
- **Scalability Limitations:** The database clustering logic (e.g., spatial distance calculations within the `VerificationEngine` via Python logic) is not optimized for geospatial queries at scale. Processing tens of thousands of simultaneous reports would require transitioning to PostGIS or a dedicated spatial database, as well as distributed caching.

## 4. Requirements for Production Deployment

Before this system can be deployed in a live municipal environment, the following improvements are required:
1. **Migration to Production Database:** Replace SQLite with PostgreSQL/PostGIS for robust concurrent transactions and native geospatial clustering.
2. **Robust Security and Identity Management:** Implement enterprise-grade authentication for officers and rate-limiting/CAPTCHA for citizen submission endpoints.
3. **Automated Evidence Analysis:** Integrate computer vision pipelines to pre-screen and validate citizen-uploaded imagery.
4. **Dynamic Thresholding:** Implement dynamic "Freshness" and "Priority" thresholds based on the specific issue category (e.g., urgent electrical hazards vs. non-urgent graffiti).
5. **Formal Stakeholder Validation:** Complete the pending stakeholder validation protocol and incorporate feedback from real stakeholders to refine the dashboard UI/UX.
6. **Cloud Deployment Architecture:** Containerize the application and deploy via cloud orchestration to ensure high availability during peak reporting events.
